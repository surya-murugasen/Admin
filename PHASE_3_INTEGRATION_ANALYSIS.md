# PHASE 3 INTEGRATION ANALYSIS

## 1. Current Project Registry Architecture
The current registry relies on the Central Admin `Project` database model. It captures metadata (name, stack, repo URLs, lifecycle status like `ACTIVE`, `PLANNED`). Currently, fields exist for `integrationType` and `healthCheckUrl`, but there is no mechanism to track runtime integration state, execute periodic polls, or authenticate with remote projects.

## 2. Integration Model
To support a strict separation between project lifecycle and runtime integration, we propose adding the following fields to the `Project` model:
- `integrationEnabled` (Boolean): Master switch to enable/disable polling.
- `integrationStatus` (Enum/String): `NOT_CONNECTED`, `CONFIGURED`, `CONNECTING`, `CONNECTED`, `OFFLINE`, `ERROR`, `DISABLED`.
- `baseUrl` (String): The root domain/IP of the external project API.
- `healthEndpoint` (String): e.g., `/api/system/health`.
- `statsEndpoint` (String): e.g., `/api/system/stats`.
- `lastHealthCheck` (DateTime): Timestamp of the last successful or failed poll.
- `apiVersion` (String): To handle future contract changes.

## 3. Security Model
**Selected Mechanism: Pre-shared HMAC (Hash-based Message Authentication Code)**
- **Why**: Since these are independent local projects communicating directly (Server-to-Server), HMAC ensures payload integrity and authenticity without the overhead of mTLS or the complexity of a full OAuth/OIDC handshake. A shared `INTEGRATION_SECRET` will be generated by the Central Admin and stored securely (hashed or encrypted) in the Admin DB, and passed as an environment variable to the external project.
- **Rules**:
  - The Admin signs requests to the project with the secret.
  - The Project validates the signature.
  - Secrets are never exposed to the frontend or stored in plaintext if possible.
  - No database credentials will ever be exchanged.

## 4. Standard Project API Contract
All integrated projects must implement standard endpoints:

**`GET /health`**
```json
{
  "status": "healthy | degraded | down",
  "service": "TeamTrack",
  "version": "1.0.0",
  "timestamp": "2026-09-24T12:00:00Z",
  "uptimeSeconds": 3600
}
```

**`GET /stats`**
```json
{
  "service": "TeamTrack",
  "timestamp": "2026-09-24T12:00:00Z",
  "metrics": {
    "activeUsers": 12,
    "pendingTasks": 5,
    "memoryUsageMB": 124.5
  }
}
```
*Note: The `metrics` object is purposefully generic and schema-less so each project can return what makes sense for its domain.*

## 5. Database Changes Proposed
Modify the `Project` schema in `schema.prisma`:
- Add `integrationEnabled Boolean @default(false)`
- Add `integrationStatus String @default("NOT_CONNECTED")`
- Add `baseUrl String?`
- Add `healthEndpoint String? @default("/api/health")`
- Add `statsEndpoint String? @default("/api/stats")`
- Add `lastHealthCheck DateTime?`
- Add `integrationSecret String?` // Used for HMAC signing

## 6. UI Changes Proposed
- **Dashboard**: Add summary cards for `Connected`, `Not Connected`, `Online`, `Offline`, and `Errors`. Update placeholders to show "NOT CONNECTED" rather than faking online status.
- **Project Registry List**: Add a status badge for `integrationStatus` alongside the lifecycle status.
- **Project Details Page**: Create an "Integration Settings" tab that reveals the `INTEGRATION_SECRET` (once, or allows regeneration) and form fields for `baseUrl`, `healthEndpoint`, and `statsEndpoint`.

## 7. Project-by-Project Integration Strategy
Integrations will be done sequentially to isolate issues:
1. **Admin Mock Integration**: Implement the contract inside the Admin itself to test the UI and polling engine locally.
2. **TaskFlow**: A standard Next/Node app. Easiest candidate for initial cross-project HTTP integration.
3. **TeamTrack**: Similar stack. Validate generic metrics UI capability.
4. **AI Models / Anti Spoof**: Python-based (FastAPI/Flask). Validate cross-language HMAC verification.
5. **Danggle / Pirate Hunt**: Assess if they have server runtimes capable of answering health checks. If static, mark as `NOT_CONNECTED`.

## 8. Risks
- **Network Latency / Timeouts**: Polling 7+ projects on dashboard load could freeze the UI. Polling must be handled asynchronously via background cron or standard Next.js cached fetches with low timeouts.
- **Clock Drift**: HMAC validation usually relies on timestamps to prevent replay attacks. Local machines might have drift. A small tolerance window (e.g., 5 mins) must be configured.
- **Security Exposure**: If a project's `INTEGRATION_SECRET` is leaked, an attacker could spoof health/stats or trigger internal endpoints if we expand capabilities.

## 9. Deployment Considerations
- In development, projects run on various `localhost` ports (e.g., 3000, 8000). The Admin must allow configurable `baseUrl`s.
- Environment variables for each integrated project must be updated with their respective `ADMIN_INTEGRATION_SECRET`.

## 10. Recommended Implementation Order
1. Update Central Admin Database Schema with integration fields.
2. Update Central Admin UI (Dashboard, Project Registry forms) to support new fields.
3. Build the HMAC signature utility library in Central Admin.
4. (STOP) Await approval to implement integration into the first target project (e.g., TaskFlow).
